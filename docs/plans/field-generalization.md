# 可修复字段泛化方案

> 状态：方案，未实施。
> 这份方案有两块：
> 1. **字段泛化**：把 Agent 从"只能修 `product.price_cents`"泛化为"按字段注册表修复任何登记过的字段"，用第一个新字段——同一行上的库存 `product.stock_qty`——证明泛化成立（第 3–7 节）。
> 2. **操作简化**：默认由章程跟进直到完成，只有必要时才问人；案例页只保留有绑定性的输入（第 8 节）。
> 演示数据同时服务于这两块（第 9 节）。
> 前提：不考虑旧数据兼容。所有环境（开发库、测试库、Studio 持久库）重建。

## 1. 目标与验收标准

1. **与字段无关的机制只实现一次**：回放、编译、计划、执行契约、沙箱执行、独立验证、撤销、写回、取证工具、Agent 工具、操作台展示，全部按字段注册表工作。
2. **字段特有的东西集中在一处**：每个字段的值类型、取值界限、业务写入口与模板、下游读者的解释、章程规则形状、展示格式，都挂在该字段的规格（FieldSpec）上，不散落在各层。
3. **加字段的成本可预期**：接入库存之后，再加一个同对象整数字段只需改第 7 节清单里的文件。
4. **人只做必要的判断**：常规案例里，人只需要勾选事故操作并批准一次；其余由章程跟进。页面上不再有"没有任何代码读取"的自由文本必填项。

可检验的验收：

| 阶段                    | 验收                                                                                                                                                                                                                          |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1 泛化重构（只有价格） | 现有测试全部通过，行为等价（计划、契约、报告的格式版本升到 2，内容等价）；纯函数测试用合成的第二个整数字段和合成的 copy 读者覆盖交错写；`rg "price_cents\|priceCents\|Cents\b"` 只命中第 6 节末列出的白名单，这条检查写成测试 |

**证明口径：** 库存证明的是"同一对象多个字段"与"同一值类型"两条泛化成立。值类型（枚举）与对象类型（新表）两条，本轮只预留形状并给出清单，要到真正接入时才算证明（第 10 节 P4）。

## 2. 现状：价格是怎样写死的

对全仓逐层盘点（13 个范围、约 90 个文件），与价格相关的耦合点按四类统计：

- **G 已通用**：提交与审计协议（`begin_commit` / `record_*`）、案例状态机与依赖失效、确认流程、租约与 fencing、账本与崩溃对账、封存与报告生命周期、Agent Runtime、操作台会话等。
- **R 机械泛化**：`cents` / `priceCents` / `'price_cents'` / `'product'` 这类命名和字面量。
- **S 价格语义特有**：价格入口与模板、订单复制成交价、价格区间约束、章程降幅阈值等。
- **O 单字段对象假设**：共一百多处，是这次泛化真正要解决的问题。

O 类有两个根因，外加一组数据库层的硬编码：

**根因 A：对象版本被当作字段版本。** `products.version` 是对象版本，任何一次写都 +1（`0001_schema.sql:12-13`、`0002_guards.sql:45-48`），但下游处处把它当作"价格的版本"：

- 回放引擎的版本链检查 `write.versionBefore !== before.version`（`engine.ts:576`），其中 `before.version` 是"价格上次被写后的对象版本"。两次价格写之间夹一次库存写，就会被误判为 `history_gap`。
- 增量和订单的读版本校验（`engine.ts:666`、`engine.ts:816`）、基线锚定（`engine.ts:866-917`）、收尾对账（`engine.ts:971-1010`）同理。
- 资格检查的链去重键不含字段（`audit-checks.ts:77-95`），依赖记录 `row_version` 与合并键只有对象版本（`contracts/evidence.ts:255-265`、`dependencies.ts:177-199`、`dependency-manifest.ts:80-87`）。
- 撤销按对象版本判"字段被后写"（`undo-contract.ts:95-119`、`0020_verification.sql:954-968`），写回核验假设"一次写回 = 对象版本 +1 且只写价格"（`0024_promotion.sql:697-740`）。

**根因 B：一个对象只有一个可修复字段、一个值、一套规则。**

- 策略 `scope.fields` 写成 `.length(1)`（`contracts/policy.ts:100`），规则没有字段维度（`policy.ts:29-52`、`policy-rules.ts:19-111`）。库存增量会命中价格的增量规则。
- 基线条目是 `{objectId, version, priceCents}` 且按对象去重（`confirmation.ts:96-116`），同一商品无法同时确认价格基线和库存基线。
- 编译器 `resolved` 按对象建键（`compiler.ts:843-849`），计划的 fieldRef 丢掉字段（`plan.ts:100-102`），依赖图候选节点键会撞车（`plan-dependencies.ts:40-42`），终态约束输入 `Map<productId, bigint>`（`constraints.ts:22-31`）。
- 契约 `inputVersions` 没有字段（`contracts/execution.ts:84-89`），账本 `writtenFieldSchema.field` 是 `z.literal('price_cents')`（`contracts/execution.ts:334-341`）。

**数据库机制层按列名写死**（任一处不改，加字段都会在不同阶段失败）：

| 位置                                                           | 写死的内容                                                                                         | 不改的后果                                             |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| `0007_snapshot.sql:182`                                        | 快照只复制 `product_id, name, price_cents, version`                                                | 快照里没有库存                                         |
| `0017_execution_commands.sql:79`、`:132`                       | 分支列清单；`GRANT UPDATE (price_cents, version)`                                                  | 沙箱写库存 permission denied                           |

## 3. 第一个新字段：同一行上的库存 `product.stock_qty`

| 候选                                           | 能逼出什么                                                                                                                                                                | 不能证明什么                                                                             |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| **同一行上的库存 `product.stock_qty`（选定）** | 根因 A 与 B 全部暴露：同一对象两个可修复字段、对象版本与字段版本分离、同一商品两条补丁、字段级漂移；值代数与价格相同（绝对写 + 增量），差异只来自"多字段"和"字段特有规则" | 新的值类型、新的对象类型                                                                 |
| 独立库存表 `inventory(product_id, qty)`        | 新对象类型（快照表清单、分支、对象选择器）                                                                                                                                | 每张表仍只有一个可修复字段，根因 A、B 被绕过而潜伏下来，留给下一个字段                   |
| 上下架状态 `product.listing_status`（枚举）    | 新的值类型                                                                                                                                                                | 没有增量，回放代数只用到一半；同样在同一行，但值类型和多字段两个变量同时变，出问题难定位 |

所以先上同行库存。枚举字段与新对象类型不在本轮实现，但注册表和值管线的形状为它们预留，第 7 节给出它们各自的加法清单。

库存的规格：

- 整数，单位"件"，平台界限 `0 ≤ qty ≤ INT64_MAX`。
- 写入口：`set_stock`（绝对，盘点）、`batch_set_stock`（绝对，盘点表导入）、`adjust_stock`（增量，出入库，参数带业务原因：销售出库、采购入库、报损）、`create_product` 增加初始库存。
- v1 中下单不扣库存，销售以 `adjust_stock` 记录。以后若要下单同时扣库存，还需要放宽两处现有约束，见第 11 节。

## 4. 泛化后的核心模型

### 4.1 两张注册表

`packages/domain` 中声明，数据库中有镜像表，用集成测试断言两边一致——这是项目已有的做法：`templates.ts` 与 `aftercare.operation_templates` 就是这样互相核对的。

**对象类型注册表**：`product`、`order`。每项包括表名、主键列、版本列、显示名列（如 `name`），以及快照与分支要复制的完整列清单。

**字段注册表（FieldSpec）**：

```ts
// 示意，非最终代码
{
  fieldId: 'product.stock_qty',      // 全系统唯一键，出现在所有契约里
  objectType: 'product',
  column: 'stock_qty',
  valueKind: 'int64',                // v1 只实现 int64；'enum' 预留
  bounds: { min: '0', max: null },   // 平台界限：回放结果越界即确定性冲突，不截断
  unit: 'count',                     // 语义单位：'cents' | 'count'；展示格式在操作台
  title: '库存',
  writeback: 'absolute_if_field_unchanged',
}
```

数据库镜像：`aftercare.object_types` 与 `aftercare.repairable_fields` 只由迁移写入，不可修改（同 `operation_templates` 的守卫）；迁移时与 `information_schema` 核对列存在且类型一致。

两张镜像表和 `operation_templates` 一样进入快照。资格检查核对快照里的注册表定义与适配器（TS 注册表）完全一致，不一致的快照只能调查、不能修复——回放必须用快照当时的字段定义来解释历史。

### 4.2 版本：对象版本链 + 字段值谱系

不给每个字段加版本列，保留对象版本作为唯一排序依据。

**三种版本口径**（现在的代码只用一个 `version` 同时表示三者，泛化后必须分开命名）：

| 口径                                      | 定义                                                              | 用在哪里                                                                             |
| ----------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 对象版本 `objectVersion`                  | 行上的 `version` 列，任何字段的写都 +1                            | 并发守卫：`concurrency_guard` 读、沙箱补丁的 `expectedVersion`、契约 `inputVersions` |
| 字段最后写入版本 `fieldVersion(o, f, ≤v)` | 字段 f 在对象版本 v 时，最后一次写入 f 的那次写的 `version_after` | 依赖图 `fv:` 节点、`get_field_history`、写回漂移、基线锚定                           |
| 快照水位                                  | 快照的提交序号                                                    | 判断"快照之后有没有写过该字段"                                                       |

**换算规则：**

- **对象版本链**：每个对象一条。检查"每次写的 `version_before` 等于该对象上一次写的 `version_after`"，在对象级做，与写了哪个字段无关。一个操作对同一对象写多列（例如 `create_product@2` 写名称、价格、库存）时，对象链按 `(operation, object)` 只推进一次，不能按 `operation_writes` 的行逐行推进。
- **字段谱系**：来自 `operation_writes`，它已经按 `(operation, field)` 记录版本迁移。沙箱分支没有审计表（0017:79-80 只复制 `products` 与 `orders`），但分支上用不到字段谱系：每个分支只接受一次应用；撤销的目标必须是封存分支的直接后继，状态为 `ready`，上面没有其他契约（0020:929-940）。所以撤销时目标分支上的对象版本恰好等于原应用的 `versionAfter`，对象级冲突检查是精确的，撤销一次回退该应用的全部字段。多跳后继与字段级撤销见第 11 节。
- **读的校验**：对字段 f 的 `business_value` 读，其 `object_version` 必须等于该对象在历史中此刻的对象版本；读到的值取自 `fieldVersion(o, f, ≤object_version)`。增量、订单、收尾对账都按这条规则改。
- **依赖图**：`fv:` 节点的版本是字段最后写入版本。由读构造节点时，先把 `read.objectVersion` 换算成 `fieldVersion(o, f, ≤read.objectVersion)`，否则读边与写边连不上。`concurrency_guard` 读的是 `version` 本身，仍按对象版本。
- **基线**：基线条目为 `(对象, 字段, 字段最后写入版本, 值)`。Autopilot 按 `≤` 查找，不再按精确相等（autopilot.ts:310-325）。
- **写前写后镜像记录对象的全部列**（现在只记被写的那一列加 `version`，0003:224-225）：
  - 镜像的列集取自 `object_types`（含主键、名称与全部登记列，再加 `version`），由同一个辅助函数 `aftercare.object_image(...)` 生成。`create_*` 与 `apply_field_write` 都用它，列集不会因入口不同而不一致（现在 `create_product` 的镜像不含 `product_id`，0003:282）。
  - 链检查"本步写前镜像 = 上一步写后镜像"（audit-checks.ts:543-555）不用改就能对交错写成立。
  - 资格检查新增两条：镜像的键集必须恰好等于该对象类型的列集；模板没声明写的列，写前写后必须相等。没有后一条，一次 `set_price` 顺手改了库存并如实记进镜像，链检查与末态对账都会放行。
  - 订单对账（audit-checks.ts:664-674）可以从下单时版本那一步的镜像直接取到价格。取证的"价格来源"查询（snapshot-reader.ts:163-164）按 `version_after = 下单版本 AND field = 价格` 精确查找，镜像修不好它，改为按字段谱系 `version_after ≤ 下单版本` 取最后一次价格写。
- `orders.price_version` 改名 `orders.product_version`：它本来就是"下单时商品的对象版本"。

这样做的理由：审计已有字段维度，写入协议只多记几列镜像；对象链仍是唯一的顺序依据，资格检查与 fencing 的论证不变。

### 4.3 值：规范文本 + 值类型

所有契约（基线、计划、补丁、契约输入钉、账本、报告、写回目标）中的值统一为 `{ fieldId, value: <规范文本> }`，编解码由 FieldSpec 的 `valueKind` 决定。int64 仍是十进制字符串、`bigint` 运算，不经浮点。数据库侧 `repair_field_versions` 等表改为 `value_before / value_after text` 加 `field_id` 外键，值域由通用函数 `aftercare.assert_field_value(field_id, text)` 按注册表检查。

### 4.4 写入语义：通用语义种类，模板按写入字段声明

`semantics.ts` 从"每个模板一个价格语义"改为"每个模板、每个被写的可修复字段一个通用语义"：

| 语义种类   | 含义                                           | 回放                                           |
| ---------- | ---------------------------------------------- | ---------------------------------------------- |
| `create`   | 值由参数给出                                   | 起点                                           |
| `absolute` | 新值 = 参数，旧值只作并发守卫                  | 事故则省略；之后按策略保留为独立覆写或未决     |
| `delta`    | 新值 = 读到的值 + 参数（要求数值型）           | 按策略在纠正后的输入上重算或未决               |
| `copy`     | 把读到的值复制进一个不可修复的对象（订单单价） | 不修复，只算出回放后应复制的值，列为受影响读者 |

示例：

```ts
add_price_delta@1  → [{ field: 'product.price_cents', kind: 'delta', param: 'delta_cents' }]
adjust_stock@1     → [{ field: 'product.stock_qty',   kind: 'delta', param: 'delta_qty' }]
create_product@2   → [{ field: 'product.price_cents', kind: 'create', param: 'initial_price_cents' },
                      { field: 'product.stock_qty',   kind: 'create', param: 'initial_stock_qty' }]
create_order@1     → [{ field: 'product.price_cents', kind: 'copy', into: 'order.unit_price_cents' }]
```

注册表校验强制两条边界：

1. **除 `create` 外，每个操作实例最多写一个可修复字段。** 事故确认仍是操作级（确认一个操作即省略它的全部可修复写），这条边界保证"操作级 = 字段级"，不需要字段级事故确认。
2. **`create` 不能被确认为事故**，只有 `absolute` 与 `delta` 可以省略。现有编译器已经如此（compiler.ts:1065），这里写成注册表规则。因此 `create_product@2` 一次写两个可修复字段不会破坏第 1 条。
3. **一个操作只写一个对象的一次版本迁移**（audit-checks.ts:266-275），v1 保持不变。
4. `delta` 只能用于数值型字段。

资格检查（`audit-checks.ts:295-335`）里"写后镜像等于参数描述的状态"现在逐操作类型手写；改为由语义表推导：absolute 检查写后值 = 参数，delta 检查写后值 = 写前值 + 参数，create 检查写后值 = 参数。价格专用的 case 因此变成通用代码。

### 4.5 策略：每条规则带字段

- `scope.fields` 改为 `min(1)`。
- 对象选择器加对象类型：`{ kind: 'all', objectType }` 与 `{ kind: 'ids', objectType, ids }`。
- `deltaReplayRules`、`overrideRetentionRules` 每条必须带 `field`；`overrideRetentionRules.operationTypes` 必须是该字段的 absolute 类操作，由注册表校验。
- 终态约束改为通用形状：`value_range { field, objects, min, max }` 与 `uniform_value { field, objectIds }`。价格区间就是价格字段上的 `value_range`。
- 平台界限来自 FieldSpec，不来自策略；越界的反例码从 `negative_final_price` / `amount_out_of_range` 改为 `value_out_of_bounds`（携带字段与界限）。

`RuleSubject` 加 `field`，规则只匹配同字段的写。

### 4.6 下游读者：通用部分 + 字段钩子

- **通用**：任何对受影响字段有 `business_value` 读、本身又不写该字段的操作，都列为"受影响读者"（计划中的仅受影响项）。`copy` 语义额外给出"回放后应复制的值"。
- **字段钩子**：价格提供"订单差额 = 数量 × (成交价 − 回放价)"的金额解释，作为报告里的订单差额清单。库存 v1 没有读者。
- 撤销的读依赖检查 `no_order_read_repaired_version` 改为通用的 `no_reader_of_repaired_value`。分支上没有 `operation_reads`，所以由注册表为 `copy` 语义声明下游持久表的**读版本列**（价格：`orders.product_version`），检查只针对被修复的字段：撤销价格修复时看订单，撤销库存修复时没有读者。库存修复之后下的单只读价格，不会被误判为读冲突。

### 4.7 数据库机制层：注册表驱动

| 做法                         | 说明                                                                         | 优点                                                                   | 缺点                                                         |
| ---------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------ |
| A. 每个字段手写一份 SQL 分支 | 执行器、diff、写回各加 `CASE field`                                          | 最直白                                                                 | 每加一个字段改七八个函数体，经评审的函数摘要随之全变，重复多 |
| **B. 注册表驱动（推荐）**    | 机制函数体固定；列名只从注册表镜像表按 `field_id` 取，用 `format('%I')` 引用 | 加字段不改机制函数体，摘要稳定；"补丁只来自契约、只改登记列"的论证不变 | 动态标识符需要严格约束（见下）                               |
| C. 由 TS 注册表生成 SQL      | 迁移时代码生成每字段静态 SQL                                                 | 生成结果可读                                                           | 多一套生成器；评审对象变成生成器加生成物                     |

选 B，约束如下：

- 标识符只来自 `repairable_fields` / `object_types`：这两张表只能由迁移写入，不可修改，迁移时核对 `information_schema`。任何函数都不接受调用方传入的列名或表名。
- SQL 类型由 `value_kind` 经固定的 `CASE` 映射（`int64 → bigint`），不取自注册表文本。
- 分支的列级授权按注册表生成：`GRANT UPDATE (<登记列>, version)`。
- 两张注册表加 `reject_history_mutation` 守卫，进入快照复制与摘要，纳入 `COVERED_TABLES`（manifest.ts:125-137），由独立验证器重核。动态列清单的完整性因此有闭环证明。
- 执行器以 `SECURITY DEFINER` 归属 `aftercare_sandbox_owner`，只给它两张注册表的 `SELECT`，不给其他 `aftercare` 表的权限。
- 分支上写死价格的守卫与辅助函数全部改为注册表驱动：`guard_branch_product_update` 的 `price_cents < 0`、0017:94 的 `CHECK (price_cents >= 0)`、固定签名的 `branch_products()`（改为通用 jsonb 行接口）、`relation_digest` 的 `NOT IN ('products','orders')`（0016:547）、checks.ts:1298-1301 的 `table !== 'products'`。
- 数据库不允许在 CHECK 里写子查询。所以 `operations_type_known`（0001:95-97）、`operation_templates_type_known`（0005:16-18）、批次类型（0001:76、0001:99）、`object_type IN ('product','order')`（0001:120、0001:139）改为指向 `operation_templates`（加 `is_batch` 列）与 `object_types` 的外键。

各机制的改法：

| 机制           | 改法                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 快照、分支复制 | 列清单取自 `object_types`；内容摘要输入里的列名随之来自注册表                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 执行器         | **同一对象一次 UPDATE**：把该对象所有被修补的字段一起写，对象版本只 +1，与 `create_product` 一次写多列一致。账本按 `(对象, 字段)` 每行一条，共享同一次 `V → V+1`。补丁的 `expectedVersion` 是快照对象版本，不存在中间版本，执行器、事后 diff、撤销、导出 SQL 都不会撞上 `V+1`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 独立 diff      | 改为整行 `jsonb` 对比：分支与快照之间任何列的变化都必须恰好落在契约足迹内，被修补对象的版本恰好 +1。`FULL OUTER JOIN` 出现增删行（任一侧为 NULL）时，先拒绝再展开列。不可修复的登记表（订单）做整表摘要比对。验证器（checks.ts）的 `preImage`、足迹、保留、未决、隔离检查全部按 `(对象, 字段)` 建键：现在按 `objectId` 建允许集合，同一对象上改了未授权字段也能通过，这是安全缺口                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 写回           | 单一受控入口 `guarded_restore_fields(targets)`：在**一次提交**里，按字段分组，每组落成该字段自己的批量绝对写（价格是批量改价，库存是批量盘点）；每个 `(对象, 字段)` 一个操作，遵守第 4.4 节第 1 条。为此去掉 `batches.commit_seq` 的 `UNIQUE`（0001:72），一次提交可以有多个批次；`promotions.batch_id` 改为 `batch_ids`；操作的 `ordinal_in_commit` 在整次提交内连续（`1..N`），不是每个批次从 1 开始。资格检查的提交组成检查（audit-checks.ts:377-409）改为按提交分组：同一提交里每个批次的操作数等于它的 `target_count`，所有操作序号为 `1..N`，单操作提交不含批次。核验（`check_promotion`）不再假设"快照版本 + 1"（0024:697-741），改为按字段谱系：写回之后该字段没有后写、且当前值等于目标值，判 `matches`；有后写，判 `superseded_by_later_write`。同一提交里另一个字段的批次把对象版本再推一格，不影响判断 |
| 撤销           | 目标为直接后继分支（见第 4.2 节）；撤销补丁按对象合并为一次 UPDATE，回退该应用在此对象上的全部字段，`expectedVersion` 为原应用的 `versionAfter`；读依赖按注册表声明的读版本列、只看被修复字段（第 4.6 节）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Autopilot 守卫 | "补丁字段 ⊆ 章程里有信封的字段"，替代 `field <> 'price_cents'`（0023:728）；`guard_autonomy_confirmation`（0023:628-649）同样校验被确认的操作只写章程里的字段                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

业务写入口仍按字段写（它们就是业务 API），但共用一个通用写助手 `apply_field_write(field_id, mode, ...)`（由现在的 `apply_price_write` 泛化而来）。每个字段的入口只是带类型参数的薄包装。

### 4.8 写回：字段级漂移

- 漂移判断从"对象版本变了"改为"该字段在快照水位之后被写过"：查源库 `operation_writes` 中同对象、同字段、提交序号大于快照水位的写。其他字段的写不阻止写回——库存在源库里持续变化，不影响价格写回。
- 写回的并发守卫仍是对象行锁加字段级检查。写入时对象版本可能已经因为别的字段前进，所以写回不以"对象版本 = 快照版本"为前提，核验也按实际记录的写入进行（见第 4.7 节）。
- 写回模式由 FieldSpec 声明。v1 两个字段都是 `absolute_if_field_unchanged`。库存这类高频变动字段漂移多，会触发章程的有限次重开，见第 11 节。

### 4.10 章程与 Autopilot

现有章程的事故规则、批准信封与写回信封都按价格写（降幅 ≥15%、单项 ≤¥200、相对 ≤200%）。改为按字段，**三类规则都带字段**：

```yaml
fields:
  product.price_cents:
    incident:
      {
        operationTypes: [batch_set_price, set_price],
        direction: decrease,
        minRelativeChangeBps: 1500,
      }
    approval: { maxAbsoluteChange: "20000", maxRelativeChangeBps: 20000 }
    promotion: { maxAbsoluteChange: "20000", maxRelativeChangeBps: 20000 }
  product.stock_qty:
    # 相对与绝对任一满足即算事故：120→85 是 29%，15→40 是 167%，都能命中；
    # 只有绝对阈值会漏掉小幅错位，只有相对阈值会被 "0 → N" 卡住。
    incident:
      { operationTypes: [batch_set_stock], minRelativeChangeBps: 2000, minAbsoluteChange: "50" }
    approval: { maxAbsoluteChange: "500" } # 不设相对变化：库存从 0 补到 N 很常见
    promotion: { maxAbsoluteChange: "500" }
```

- **信封的形状按值类型定义，不按字段定义。** int64 用绝对变化与可选的相对变化；enum 用允许的取值迁移。
- **事故规则里，相对与绝对两个阈值是「或」的关系。** 库存用单一绝对阈值（例如 ≥50 件）会漏掉 120→85 这种错位（Δ=35），用单一相对阈值会被「0 → N」卡住。两个都给，任一满足即命中。
- **"从 0 变为非零"的拒绝只在配置了相对变化时适用。** 现在 SQL 与 TS 三处都无条件拒绝（0023:739、0024:406、rules.ts:142-150），库存的"0 → N"会被误拒。
- **`maxChangedObjects` 按 `(objectType, objectId)` 去重计数。** 现在按补丁条数计（`jsonb_array_length`），同一商品两个字段会被算成两个对象。
- **Autopilot 判定事故范围时，候选操作要带上它写了哪个字段**（现在只有 `product/<id>`，autopilot.ts:247-298），从 `get_operation_detail` 或字段历史得到。
- **两种"不匹配"要分开处理：**
  - 操作写的字段在章程里、但不满足事故规则：按 `onNoMatch` 处理，可以 decline。
  - 操作写的字段**不在章程里**：一律升级给人，不能 decline（现在 autopilot.ts:295-297 会落到 decline）。

### 4.11 操作台展示

- 对象显示为"名称 · ID"（例如 `手摇磨豆机 · r03-grinder`）。名称由视图层从快照读取，按不可信文本渲染，不进计划和摘要。
- 值按语义单位格式化：`cents` 显示 `¥299.00`，`count` 显示 `40 件`，枚举显示中文标签。变化显示为 `¥299.00 → ¥2.99（−99.0%）`。int64 格式化直接处理十进制字符串，不经过浮点。
- 字段标题、操作类型、操作人显示名都改为中文；演示角色的显示名在场景库里登记。

## 8. 操作简化：默认自主跟进，页面只问必要的

这一节回应三点要求：不用先告诉 Agent「自主处理」；一个案例默认持续跟进到完成，必要时才问人；案例页不要那么多防御性的必填输入。

### 8.1 现状：为什么现在要说一句才自主

不是一道门，是四道门串联：

1. 开案的 `autonomous` 默认 false（actions.ts:83、assistant/tools.ts:224-229）。
2. 助手的提示词规定「只有用户明确说自主处理/按章程处理才置 true」（assistant/prompt.ts:68），没有章程时还会说「不能以 autonomous=true 开案」（assistant/prompt.ts:45-48）。
3. 全仓只有 `startAutonomousRun` 会 enroll（autonomy/start.ts:96）。非自主开案的运行永远不进 Autopilot 的视野，而且没有「事后纳入章程」的入口。
4. 助手回合由用户发言驱动，`wait_for_case` 最多等 60 秒（assistant/turn.ts:165-262、assistant/tools.ts:340）。开案后没人再说话，就没有人再看这个案例。真正在后台逐轮推进的只有 daemon 里的 Autopilot（daemon.ts:210）。

第 3、4 两点合起来说明：**「持续跟进」缺的是驱动，不是耐心。** 把等待时间调长没有用。

### 8.2 一条不能越过的线

章程是唯一的授权来源（0023_autonomy.sql:99-128），而且只能由持 `delegate_autonomy` 的业务负责人登记。**「默认自主」不能变成「系统替人授权」。**

所以做法是：**部署时由有权人登记一次默认章程，此后所有案例默认纳入。** 用户不需要再对每个案例说「自主处理」，但授权链上仍然有一个人签过字。这和第九阶段现有的做法一致——演示环境就是这样由 `ops:demo-owner` 登记章程的（console/src/demo.ts:49-94, :366-372）。

| 做法                                | 说明                                                  | 结论                                                   |
| ----------------------------------- | ----------------------------------------------------- | ------------------------------------------------------ |
| A. 系统内置一份默认章程并自动登记   | 用户完全无感                                          | 不做。系统自己给自己授权，章程失去「人签字」的意义     |
| **B. 部署时有权人登记一次（推荐）** | `pnpm ops charter:register` 执行一次，之后默认 enroll | 采用。用户的日常操作从「每案说一句」降到「部署时一次」 |
| C. 保持现状                         | 每个案例都要说一句                                    | 不满足要求                                             |

默认章程的内容要点（相对演示章程）：**P2 先登记只覆盖价格的版本，P3 接入库存后再登记第二版加入 `product.stock_qty`**（章程表是追加式的，0023:31-52，旧版本保留、以最新在用版本为准）；`onNoMatch` 取 `escalate`；`recovery.resumableReasons` 三项齐全、`maxResumesPerRun` 大于 0；`maxDriftReopens` 至少 1；`promotion.enabled: true`。库存的事故规则要同时给相对与绝对阈值（见第 4.10 节），否则场景 4、7 会漏掉小幅错位。包络取保守值，理由见 8.9。

### 8.3 默认持续跟进

- **默认 enroll**：`autonomous` 默认为 true，条件是"有在用章程且开关开启"。没有章程时，开案照常进行，但要在回复里明说"案例在人工跟进模式，因为这些事项需要你来定"，不静默降级。
- **先判定，再建案**。现在 `submitIncident` 先建案、再调 `startAutonomousRun`（actions.ts:322-342）。默认自主后，一旦没有章程或开关关闭，就会留下一个没有运行的空案。要先判定开关与唯一章程，再决定走自主还是人工。
- **多份在用章程会让自主启动被拒**（`charter_ambiguous`，autonomy/start.ts:58-68）。默认自主需要约定"单份默认章程"。
- **提示词反过来写**：只有用户明确说"不要自主处理 / 我要自己批"时才置 false。删掉"没有章程就不能自主"的表述，改成"没有章程，告诉你缺什么"。
- **接管，而不是事后纳入**。第 8.2 节说的"把已有案例纳入章程"要换一种实现：`autonomy_enroll` 拒绝纳入不是该 autopilot 启动的运行（0023_autonomy.sql:511-514），而 `started_by` 不可改（0021_agent.sql:215-221）。这个守卫应当保留——它保证 Autopilot 只处理自己启动的运行。所以不做事后纳入，改做**接管**：以 autopilot 身份在同一案例上启动一个新运行，旧运行作为历史保留。
  - `startAutonomousRun` 要支持在已有案例上启动，并接受 `acknowledgeIsolation`（现在没有这个参数，隔离案例会直接撞 AC603，0021:707-711）。
  - 走这条路时，仍要先校验**人类调用方**自己的 `manage_case`（像 actions.ts:313 那样），不能因为是 autopilot 启动就跳过。
  - `rerun` 与隔离重开都改走这条路径。现在它们都不 enroll（actions.ts:378-404），一次误操作就让案例永久脱离跟进。
- **助手不再负责盯案例**。跟进本来就该由 daemon 里的 Autopilot 做：它每轮处理已 enroll 的运行（daemon.ts:204-211）。助手改成"用户问的时候汇报当前状态"，`wait_for_case` 可以保留也可以删掉——它从来不是持续跟进的机制。
- **停下来等人时要有提示**。现在案例进入 `awaiting_answer` / `awaiting_approval` / `paused`，只有人自己去看页面才知道（reads.ts:179-187）。操作台的案例列表已经有 `openQuestions` 与阶段，把"待你处理"的案例排在前面并加显著标记即可，不需要新表。
- **轮询不能饿死人**。daemon 每轮取 50 个可运行运行（agent-store.ts:86-90）与 50 个可处理案例（autonomy-store.ts:75-90），两者都包含长期等待人工的事项。积压到 50 个待人案例，后面的新案就轮不到。改为分别查询"可自动推进"与"等人"的两类，或按加入时间分页。

### 8.4 四处"静默停住"必须改成"问人"

"必要时才问人"的反面是"有时候永远不问"。现在有四处会静默停住或静默漏掉：

| 位置                                                                | 现状                                                                                                                                         | 改法                                                                                                                                                          |
| ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### 8.6 写回必须有一条人工链路

这是第 8.4 节之外的一个欠缺，而且是**现在就存在、简化后会更容易撞上**的：写回源库只有 Autopilot 的 `promoteUnderCharter` 一条执行路径（daemon.ts:253-256）。当写回超出章程包络而被升级给人（autopilot.ts:485-488），或案例根本没 enroll 时，全仓没有人工批准写回、触发写回的界面、动作或后台任务：`promotion.tsx` 只读，`operatorWork` 只处理撤销（daemon.ts:143-183）。

简化后默认自主，大部分案例走章程，但**场景 1 和场景 7 必然因价格变化远超包络而升级给人**（降价 99% 恢复原价相当于上涨 9900%）。没有人工链路，案例就停在"已升级"这一步。

要做的是：

- 案例页"报告与产物"里增加写回审批卡：展示写回目标、逐字段变化、包络判定结果与未决项，人点一次批准。底层的 `approve_promotion` 与 `promote` 已经存在（0024:416、:530），缺的是操作台动作与页面。
- daemon 的 `operatorWork` 增加"已批准、待写回的晋升"这一类，像撤销执行那样由后台推进，而不是等人再点一次。
- 升级后案例必须出现在待办里（依赖第 8.4 节的升级可见性修复）。

### 8.7 简化后，一个人要做什么

| 情形                                                      | 人要做的事                                                                 |
| --------------------------------------------------------- | -------------------------------------------------------------------------- |
| 章程覆盖、且变化在包络内的案例                            | 一次都不用动手。事故范围、基线、策略由章程代答，执行批准也在包络内自动完成 |
| 变化超出批准包络（例如场景 1、7 把 ¥2.99 恢复成 ¥299.00） | 批准一次（未决域已默认全选），写回再批准一次。这是「必要时问人」的主要情形 |
| 章程只覆盖了部分操作                                      | 看一眼被升级的未命中项，决定是否把它们也算事故                             |
| 章程没覆盖的操作或字段                                    | 收到一条「需要你决定」，回答后继续                                         |
| 预算或模型连续失败                                        | 章程允许的范围内自动恢复；超出范围才问人                                   |
| 写回核验不一致                                            | 人处置，系统不自动重写也不回滚                                             |
| 上次被隔离                                                | 确认后才重开                                                               |

### 8.8 与字段泛化的关系

两件事要一起做，不是巧合：

- 接入库存后，页面上会出现**两个字段的基线、两个字段的未决域**。不做这一节的简化，多字段案例（第 9 节场景 7）会比现在更重。
- 简化依赖泛化后的形状：未决域按字段、基线条目带字段、策略规则带字段。所以这一节落在 P2，排在泛化之后。
- 反过来，泛化的验收里已经包含「同一案例同时修两个字段」，它只有在页面按字段呈现、且不需要人逐个填说明时才可用。

按第 8 节的设计推演场景 7（价格与库存都出错，同一案例）：

| 环节                                    | 谁做                                                                                                                                     |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 事故范围（价格导入 + 盘点导入两批操作） | 章程命中则代答；两批都要在同一个问题里给出，Agent 的提示词与协议驱动现在假设单批次（prompt.ts:35、protocol-driver.ts:215-221），要一并改 |
| 价格基线 + 库存基线                     | 章程代答（两字段各一条，基线条目带字段）                                                                                                 |
| 回放策略                                | 章程取登记的版本                                                                                                                         |
| 澄清（若有）                            | 章程代答或升级给人                                                                                                                       |
| 执行批准                                | **升级给人一次**：价格从 ¥2.99 回到 ¥299.00 超出包络                                                                                     |
| 写回批准                                | **升级给人一次**：同一原因                                                                                                               |

也就是说，双字段案例在简化后是「一次执行批准 + 一次写回批准」，与单字段案例相同，不会因为多了一个字段而多问一次。这就是第 8 节要保证的东西。

### 8.9 风险

- **默认自主的最大风险是章程本身。** 包络只限制损失范围，不判断该不该动；章程写错，系统会正确地执行错误的规则（autonomy-protocol.md:516-519）。缓解：默认章程取保守包络；报告里明示由章程代答的每一项；一键关闭始终保留给人（0023:107-109）。
- **去掉自由文本会降低审计的「人话」程度。** 缓解：自动陈述里必须带决定动作、对象、摘要、证据引用，而不只是「操作员已确认」。
- **默认 enroll 可能让人不知道案例已交给 Autopilot。** 缓解：案例页常驻标记；首次开案时说一句「这个案例将由章程跟进，需要你时会通知你」，之后不再重复。
- **接管会产生多个运行。** 接管是在同一案例上以 autopilot 身份再启动一个运行，而不是把旧运行交给章程。旧运行保留为历史，案例页要能区分「谁启动的、在不在章程下」，否则人会以为是同一个运行。
- **简化后页面上的信息更少，判断更依赖展示质量。** 未决域默认全选，意味着人必须真的看见那几项；如果折叠或截断，就等于让人「盲批」。验收里要有一条：未决域清单在批准前完整可见。

## 9. 演示场景

### 9.1 原则

- **数据库里只有普通业务操作**，不含事故标签。场景的"背景说明"只给演示者看，不写入数据库，不进入任何模型上下文。建议描述只写现象。
- **隐藏答案只在测试里**：评测用例引用场景的步骤 id 定义真相，场景库本身不含答案。
- **一眼能看懂**：中文商品名；价格是常见价位且彼此错落；错误形态肉眼可辨（磨豆机 ¥299.00 变成 ¥2.99）；操作人有显示名（导入任务、运营·小李、门店收银、仓管·老王）。
- **一个场景库供所有演示与评测复用**：新增 `packages/scenarios`，供 `ops demo:init --scenario <id>`、`demo:autonomous --scenario <id>`、`demo:agent --scenario <id>` 与评测使用。删除 `storage/scripts/seed-demo.ts` 与 `db:seed`，以及 console、agent 脚本里各自手写的数据；各阶段的协议演示也从场景库取数据，需要特殊形状时在场景库里加场景。
- **ID**：`r03-grinder`，即轮次加英文短名。轮次递增，不用随机十六进制。

### 9.4 各场景的数据

**场景 1：调价表"元"被当成"分"。** 调价表填的是"元"，导入任务按"分"写入。

| 步骤 | 操作人    | 操作                                                                                            |
| ---- | --------- | ----------------------------------------------------------------------------------------------- |
| 1    | 导入任务  | 批量改价：磨豆机 ¥2.99、手冲壶 ¥1.89、滤杯 ¥0.79、滤纸 ¥22.00（这一条是合法促销）、电子秤 ¥1.29 |
| 2    | 运营·小李 | 手冲壶加价 ¥10.00（→ ¥11.89）                                                                   |
| 3    | 运营·小李 | 滤杯单独改价为 ¥69.00                                                                           |
| 4    | 门店收银  | 电子秤卖出 2 件，按 ¥1.29 成交                                                                  |

- 批次里有一条合法改价，需要逐条确认。
- 手冲壶的加价在纠正后的基数上重算为 ¥199.00。
- 滤杯的单独改价由策略决定保留还是标为未决。
- 订单差额清单显示电子秤那一单少收 ¥255.42。

**场景 2：调价任务重试。**

| 步骤 | 操作人    | 操作                                                                  |
| ---- | --------- | --------------------------------------------------------------------- |
| 1    | 调价任务  | 手冲壶 +¥20.00（¥189.00 → ¥209.00）                                   |
| 2    | 调价任务  | 手冲壶 +¥20.00（→ ¥229.00）。"超时重试"只写在演示者卡片里，不进数据库 |
| 3    | 运营·小李 | 手冲壶 −¥10.00 促销（→ ¥219.00）                                      |

现象："手冲壶比调价单上贵了 ¥20"。应得 ¥199.00。

**场景 3：季节性降价（诱饵）。** 导入任务把全部商品降价 10%（磨豆机 ¥269.10 等），之后正常卖货和改价，P3 再加正常的出入库。全部是有意变更：Agent 应当问清意图后不修复。

**场景 4：盘点表错位一行。** 导入前库存为 40 / 120 / 85 / 300 / 15。

| 步骤 | 操作人    | 操作                                                                                      |
| ---- | --------- | ----------------------------------------------------------------------------------------- |
| 1    | 盘点导入  | 批量盘点：每个商品都写成了下一行的数：磨豆机 120、手冲壶 85、滤杯 300、滤纸 15、电子秤 40 |
| 2    | 门店收银  | 磨豆机销售出库 −3                                                                         |
| 3    | 采购      | 手冲壶采购入库 +50                                                                        |
| 4    | 仓管·老王 | 滤纸人工复盘为 296                                                                        |

现象："昨天导入盘点表后，几款商品的库存对不上"。应得：磨豆机 37、手冲壶 170、滤杯 85、滤纸 296（复盘覆盖被保留）、电子秤 15。

**场景 5：纠正后超卖。** 电子秤原库存 15 件（目录值），盘点导入误写为 40 件；系统据此又卖出 20 件，在案记录为 20 件。在纠正后的基数上重算得到 15 − 20 = −5，判为 `value_out_of_bounds`。编译给出反例，由业务决定怎么处理，例如用策略声明这几笔出库不重算，该字段标为未决。系统不会截断成 0。

**场景 6：价格出错，库存照常进出。**

| 步骤 | 操作人    | 操作                              |
| ---- | --------- | --------------------------------- |
| 1    | 运营·小李 | 磨豆机改价，¥299.00 误输成 ¥29.90 |
| 2    | 门店收银  | 磨豆机销售出库 −2                 |
| 3    | 采购      | 磨豆机采购入库 +20                |
| 4    | 门店收银  | 磨豆机销售出库 −1                 |

现象："磨豆机标价好像少了一个 0"。验收断言：

- 价格恢复为 ¥299.00，库存保持 57 件，库存一列不动。
- 回放时不出现 `history_gap`：对象版本在价格两次写之间前进了 3。
- 快照之后源库又卖出 1 件，价格写回照常成功，因为漂移按字段判断；写回核验按实际写入通过。
- 闭环：独立验证 → 受控导出与演练 → 在直接后继分支上撤销价格修复（价格回到快照值，库存不动）；Autopilot 按章程代答、批准、写回并核验。

**场景 7：价格和库存都出错。** 场景 1 的错价导入与场景 4 的错位盘点作用在同一批商品上，之后有正常卖货。一个案例同时确认两次导入为事故：

- 计划中同一商品有价格和库存两条补丁。
- 一份契约、一次批准。
- 沙箱中每个商品一次写入两个字段，对象版本 +1，账本按字段记两行。
- 报告按字段列出修改。
- 闭环：撤销整次修复，两个字段一起回到修复前；写回在一次提交里产生价格、库存两个批次，`check_promotion` 逐条核验；源库库存漂移时触发章程的有限次重开。

## 11. 明确的边界与风险

1. **事故粒度仍是操作级。** 配合第 4.4 节的四条边界，操作级就等于字段级。以后若有模板要同时写两个可修复字段（例如"商品资料导入"一次写价格和库存），需要把事故集合条目扩成 `{ operationId, fields }`。回放本来就逐字段进行，改动只在事故集合契约和引擎判断是否为事故的那一处。
2. **资格判定保持对象级。** 一个字段的审计问题会让整个对象只能调查，不能修复。这是保守方向。镜像含全部登记列，末态对账覆盖所有登记字段，不会出现"对象级合格却有字段没核对过"。完整性锚点（0014:846-884）同样保持对象级，代价是跨字段的过度失效。
3. **撤销保持单跳。** 撤销只以封存分支的直接后继为目标，对象级冲突检查在那里是精确的。若以后允许多跳后继，例如 B1 修价格并封存、B2 修库存并封存、B3 撤销 B1，需要沿 `branch_lineage` 汇总应用账本得到分支上的字段谱系。分支表的写权限只在不可登录的 `aftercare_sandbox_owner` 上（0017:132），`apply_repair` 在同一事务内把独立 diff 记入账本（0018:962、0020:2031-2037），这个汇总有可靠的来源。另外，后继分支上绑定同一商品另一字段的修复，需要放宽"契约输入版本等于快照版本"（0017:276-298）。两者都不在本轮。
4. **高频变动字段的写回。** 字段级守卫下，库存仍会因为源库持续出入库而漂移，触发章程的有限次重开。"补偿增量写回"（把修复值 − 快照值作为增量写回）需要新的策略规则和业务确认，不在本轮。
5. **下单扣库存不在本轮，也不是"模型已支持"。** `create_order@2` 同时 copy 价格、对库存做 delta −quantity，在"最多一个可修复字段"上没问题，但还要放宽两处：
   - 资格检查"一个操作只写一个对象的一次版本迁移"（audit-checks.ts:266-275）：它会写订单和商品两个对象。
   - 编译器的外来读检查（compiler.ts:152-163）：它读价格、写库存。
     另外语义声明要加参数的符号。
6. **动态标识符。** 约束见第 4.7 节。另加测试：用非法注册表行（不存在的列、类型不符）验证迁移校验会拒绝；任何机制函数都不接受调用方传入的列名或表名。
7. **格式号与摘要。** plan / contract / confirmation / policy / question / report / export / promotion / charter 的格式号统一升到 2，旧数据不迁移。
8. **迁移原地改写。** 不考虑兼容，所以直接改 0001–0025 中的相关段落，schema 读起来就是设计本身，也不会留下价格专用版本的函数体。所有库重建，包括 Studio 持久库。
9. **审计行变大。** 镜像记录全部登记列，每条审计的镜像随登记列数线性增长。登记列是少数业务字段，可以接受。
